# Reusable Key Handling Library for p5.js Apps

## Problem Statement

Currently, each p5.js app in the monorepo (monochromifier, duo-chrome, dragline, etc.) must manually implement key event handling with individual `return false` statements for each handled key. This approach:

- Creates repetitive code across apps
- Is error-prone (easy to forget `return false` for specific keys)
- Doesn't prevent browser shortcuts for unhandled keys
- Lacks consistency in key handling patterns
- Makes it difficult to avoid browser shortcut conflicts

The monochromifier implementation required adding `return false` to each individual key handler to prevent the blanket prevention of all browser shortcuts.

## Requirements

### Functional Requirements
- Prevent browser default behavior only for keys actually handled by the app
- Support modifier keys (Ctrl, Cmd, Shift, Alt) cleanly
- Work seamlessly with p5.js event system
- Support context-sensitive handlers (e.g., paint mode vs normal mode)
- Provide clear, intuitive API for creative coding workflows

### Non-Functional Requirements
- Minimal performance impact
- Easy to integrate into existing apps
- Good debugging/development experience
- Consistent behavior across apps
- Accessible and well-documented

## Technical Approach

### Option 2: Small Reusable Helper Function

```javascript
// In @genart/p5-utils or new @genart/key-handling library
const createKeyHandler = (keyMap) => {
  return (p5Instance) => {
    const handler = () => {
      const key = p5Instance.key.toLowerCase()
      const modifiers = []
      if (p5Instance.keyIsDown(p5Instance.CONTROL)) modifiers.push('ctrl')
      if (p5Instance.keyIsDown(91)) modifiers.push('cmd') // 91 = cmd key
      if (p5Instance.keyIsDown(p5Instance.SHIFT)) modifiers.push('shift')
      
      const keyCombo = modifiers.length ? `${key}+${modifiers.join('+')}` : key
      
      if (keyMap[keyCombo] || keyMap[key]) {
        const handler = keyMap[keyCombo] || keyMap[key]
        handler()
        return false // Prevent default only for handled keys
      }
      // Allow browser default for unhandled keys
    }
    return handler
  }
}

// Usage in apps:
const keyHandler = createKeyHandler({
  'i': () => invertImage(),
  's+ctrl': () => saveImage(),
  's+cmd': () => saveImage(),
  '?': () => toggleHelp()
})
p.keyPressed = keyHandler(p)
```

## Implementation Steps

1. **Research Phase**
   - Audit existing key handling patterns across all p5.js apps
   - Identify common patterns and edge cases
   - Document current pain points and inconsistencies

2. **Design Phase**
   - Choose between Option 2 (simple) vs Option 3 (advanced)
   - Design API that balances simplicity with functionality
   - Create TypeScript interfaces for type safety

3. **Implementation Phase**
   - Create new library in `libs/key-handling` or extend `libs/p5-utils`
   - Implement core functionality with tests
   - Add support for special keys (arrows, function keys, etc.)

4. **Integration Phase**
   - Refactor monochromifier to use the new library (proof of concept)
   - Migrate other apps incrementally
   - Update documentation and examples

5. **Validation Phase**
   - Test across different browsers and platforms
   - Verify accessibility compliance
   - Performance testing with complex key mappings

## Testing Strategy

### Unit Tests
- Test key combination parsing
- Test modifier key detection
- Test context switching (if implemented)
- Test edge cases (special characters, international keyboards)

### Integration Tests
- Test with actual p5.js instances
- Test browser compatibility (Chrome, Firefox, Safari, Edge)
- Test on different platforms (Windows, Mac, Linux)

### User Experience Tests
- Verify common browser shortcuts work when not handled by app
- Test developer experience with clear error messages
- Validate performance with large key mappings

## Risks & Mitigation

### High Risk
- **Browser compatibility**: Different browsers handle key events differently
  - *Mitigation*: Comprehensive cross-browser testing, fallback strategies
- **Performance impact**: Complex key processing could slow down apps
  - *Mitigation*: Benchmark against current implementation, optimize hot paths

### Medium Risk
- **Migration complexity**: Existing apps have established key handling
  - *Mitigation*: Gradual migration, maintain backward compatibility
- **API design**: Need to balance simplicity with functionality
  - *Mitigation*: Prototype with real apps, gather developer feedback

### Low Risk
- **Maintenance burden**: Another library to maintain
  - *Mitigation*: Keep focused scope, good documentation, automated testing
